
## 1. Tick：行为树的“心跳”

行为树不是一次性从头跑到尾，而是会被不断地“敲一下”。

这个“敲一下”就叫 **Tick**。

你可以理解成：

```
每隔 100ms 问一次：你现在该做什么？上一步完成了吗？有没有失败？要不要执行下一个动作？
```

举个生活例子：

你叫外卖：

```
每隔一会儿看一下：商家接单了吗？骑手取餐了吗？骑手送到了吗？
```

每看一次状态，就像一次 Tick。

在机器人里：

```
每隔一段时间检查：摄像头是否准备好？编码器是否启动？RTP 是否已经推流？客户端是否还在线？
```

行为树就是靠不断 Tick 来驱动整个流程的。

---

## 2. 节点返回状态：SUCCESS / FAILURE / RUNNING

每个行为树节点执行后，一般会返回三种状态。

|状态|含义|通俗解释|
|---|---|---|
|SUCCESS|成功|这件事做完了|
|FAILURE|失败|这件事做不了|
|RUNNING|进行中|还没做完，下一次再来问|

例如“启动摄像头”这个节点：

```
StartCamera
```

可能返回：

```
SUCCESS：摄像头启动成功
FAILURE：摄像头打不开
RUNNING：正在启动中，还没完成
```

生活例子：

你去烧水：

```
SUCCESS：水烧开了
FAILURE：水壶坏了
RUNNING：正在烧，还没开
```

这个三状态非常重要，尤其是 **RUNNING**。因为机器人里的很多动作都不是瞬间完成的，比如导航、建图、推流、充电、避障，都需要持续运行。

# 二、行为树的基本节点类型

## 3. Action 节点：真正干活的节点

**Action** 就是执行动作的节点。

比如：

```
打开摄像头启动编码器开始 RTP 推流发送 MQTT 命令导航到目标点清理地图播放提示音
```

在你的项目里，Action 节点可以是：

```
SendMqttStartStreamCommandStartCameraStartEncoderStartRtpPushStopStreamReportErrorToPhone
```

通俗理解：

> **Action 就是“干活的人”。**

比如你要做饭：

```
洗菜切菜炒菜装盘
```

这些都是 Action。

---

## 4. Condition 节点：只负责判断，不干活

**Condition** 是条件判断节点。

它不执行复杂动作，只判断某个条件是否成立。

比如：

```
手机是否发起预览请求？RK3576 是否在线？摄像头是否可用？网络是否正常？是否已经有客户端在看？电量是否足够？
```

在你的推流场景中：

```
HasPreviewRequest
IsRK3576Online
IsCameraAvailable
IsClientAliveIsNetworkOk
```

生活例子：

你出门前要判断：

```
有没有带钥匙？手机有没有电？外面是不是下雨？
```

这些判断本身不干活，只返回成功或失败。

```
有钥匙：SUCCESS没钥匙：FAILURE
```

通俗理解：

> **Condition 是“检查员”。**

---

## 5. Sequence 节点：按顺序执行，“一个失败全失败”

**Sequence** 是最常用的控制节点。

它的规则是：

```
从左到右依次执行前一个成功，才执行下一个只要有一个失败，整个 Sequence 就失败
```

你可以把它理解成：

> **一串必须全部完成的流程。**

例如机器人开始推流：

```
Sequence├── 检查手机请求├── 检查 RK3576 在线├── 检查摄像头├── 启动摄像头├── 启动编码器└── 开始 RTP 推流
```

只要其中任何一步失败，整个流程就失败。

比如：

```
检查手机请求：SUCCESS检查 RK3576 在线：SUCCESS检查摄像头：FAILURE
```

那后面的“启动摄像头、启动编码器、开始推流”都不会执行。

生活例子：

你要坐高铁：

```
Sequence├── 买票├── 带身份证├── 到车站├── 安检├── 检票└── 上车
```

任何一步失败，都上不了车。

通俗理解：

> **Sequence 就是“并且”：A 成功，并且 B 成功，并且 C 成功，整个任务才成功。**

---

## 6. Fallback / Selector 节点：尝试方案，“一个成功就成功”

**Fallback** 也叫 **Selector**，意思是“兜底选择”。

它的规则是：

```
从左到右依次尝试如果前一个失败，就尝试下一个只要有一个成功，整个 Fallback 就成功全部失败，才算失败
```

你可以理解成：

> **先试方案 A，不行再试方案 B，再不行试方案 C。**

比如机器人无法推流时：

```
Fallback├── 正常启动推流├── 重启摄像头后再推流├── 重启编码器后再推流└── 上报推流失败
```

如果“正常启动推流”成功，后面的就不执行。

如果失败，就尝试“重启摄像头后再推流”。

生活例子：

你去吃饭：

```
Fallback├── 去常去的饭店├── 如果满座，去第二家├── 如果第二家也满座，点外卖└── 如果外卖也不行，泡面
```

通俗理解：

> **Fallback 就是“或者”：A 可以，或者 B 可以，或者 C 可以。**

---

# 三、修饰节点 Decorator

## 7. Decorator 节点：给子节点加规则

**Decorator** 不直接干活，它是给某个节点加一层规则。

常见的 Decorator 有：

```
重试几次超时限制取反结果循环执行等待一段时间只有条件满足才执行
```

你可以理解成：

> **Decorator 是“附加规则”。**

比如：

```
RetryUntilSuccessful└── StartCamera
```

意思是：

```
启动摄像头失败了不要马上放弃，最多重试几次。
```

再比如：

```
Timeout 5s└── WaitStreamStarted
```

意思是：

```
等待推流启动，但最多等 5 秒，超过 5 秒就失败。
```

生活例子：

你打电话给朋友：

```
Retry 3 次└── 打电话
```

意思是：

```
第一次没人接，再打第二次，最多打三次。
```

通俗理解：

> **Action 是干活，Decorator 是规定这个活怎么干。**

---

## 8. Inverter：结果取反

这是一个常见 Decorator。

它会把结果反过来：

```
SUCCESS 变 FAILUREFAILURE 变 SUCCESS
```

比如：

```
Inverter└── IsBatteryLow
```

原本：

```
IsBatteryLow 成功 = 电量低
```

加了 Inverter 之后：

```
电量不低才算成功
```

生活例子：

```
IsRaining：是否下雨
```

如果你想表达“不下雨才出门”，可以写成：

```
Inverter└── IsRaining
```

---

## 9. Retry：失败重试

机器人系统里很常用。

例如 MQTT 发送命令可能偶尔失败：

```
Retry 3 次└── SendMqttStartStreamCommand
```

含义：

```
发送 MQTT 开始推流命令如果失败，最多重试 3 次3 次都失败，才真正失败
```

生活例子：

你扫码支付：

```
第一次网络失败第二次重试第三次成功
```

那整个支付流程就算成功。

---

## 10. Timeout：超时控制

机器人动作不能无限等。

例如：

```
Timeout 5s└── WaitStreamStarted
```

意思是：

```
等待 RK3576 返回“推流已启动”如果 5 秒内等到了，成功如果 5 秒还没等到，失败
```

这个在工程里非常重要。

否则可能出现：

```
手机一直等RK3588 一直等RK3576 卡住整个系统没有响应
```

通俗理解：

> **Timeout 就是“不许无限拖下去”。**

---

# 四、并行和异步

## 11. Parallel 节点：多个任务同时做

**Parallel** 表示多个节点同时执行。

比如机器人执行任务时：

```
Parallel├── 执行导航├── 检测障碍物├── 监测电量└── 监测网络连接
```

这几个事情不是一个做完再做另一个，而是同时关注。

在你的推流场景中：

```
Parallel├── RTP 推流├── 监听客户端是否断开├── 监听摄像头是否异常└── 监听网络是否异常
```

生活例子：

你开车时：

```
开车看红绿灯看行人听导航注意油量
```

这些是同时发生的。

---

## 12. 异步 Action：耗时任务不能卡死整棵树

这是行为树工程实践里的重点。

比如“开始推流”不是一瞬间完成的：

```
StartRtpPush
```

它可能需要：

```
初始化摄像头初始化编码器创建 RTP socket启动线程等待第一帧数据
```

如果这个节点一直阻塞，行为树就卡住了。

所以它应该这样返回：

```
第一次 tick：启动任务，返回 RUNNING第二次 tick：检查是否启动完成，继续 RUNNING第三次 tick：推流成功，返回 SUCCESS
```

而不是：

```
一直阻塞在那里等结果
```

生活例子：

你洗衣服：

```
按下洗衣机开始键洗衣机运行中你不用一直站在那里不动你可以过一会儿再看
```

这就是异步 Action 的思想。

---

# 五、黑板 Blackboard

## 13. Blackboard：行为树里的共享数据区

行为树的节点之间需要传递数据。

例如：

```
手机 IPRTP 端口客户端 ID目标点坐标摄像头编号当前任务 ID错误码
```

这些数据不能每个节点自己瞎保存，所以通常放在 **Blackboard** 里。

你可以理解成：

> **Blackboard 就是一块公共白板，所有节点都可以往上写，也可以从上面读。**

在你的推流场景中：

```
Blackboard├── clientIp = 192.168.1.20├── rtpPort = 5000├── deviceId = rk3576_01├── streamId = preview_001└── retryCount = 0
```

然后节点可以这样用：

```
SendMqttStartStreamCommand 从 Blackboard 读取 clientIp 和 rtpPortStartRtpPush 从 Blackboard 读取目标地址ReportErrorToPhone 从 Blackboard 读取错误码
```

生活例子：

公司开会时，白板上写着：

```
今天目标：完成方案负责人：张三截止时间：下午 5 点当前问题：接口未联调
```

大家都看这块白板协作。

# 六、端口 Ports

## 14. Input Port / Output Port：节点输入输出

行为树里的节点通常不是写死的，而是通过端口传递参数。

比如：

```
StartRtpPush
```

它需要知道：

```
推到哪个 IP？推到哪个端口？使用哪个摄像头？
```

所以可以设计成：

```
StartRtpPush输入：- client_ip- rtp_port- camera_id
```

执行完成后，它可能输出：

```
stream_idstatuserror_code
```

这就是端口。

生活例子：

你请人送快递：

输入：

```
收件人手机号地址物品
```

输出：

```
快递单号配送状态
```

通俗理解：

> **Port 就是节点的参数入口和结果出口。**

# 七、子树 SubTree

## 15. SubTree：把复杂流程封装成小模块

当行为树越来越大时，不能所有节点都堆在一起。

可以把一部分流程封装成子树。

比如“启动推流”可以封装为：

```
SubTree: StartPreviewStream├── CheckRK3576Online├── CheckCamera├── StartCamera├── StartEncoder└── StartRtpPush
```

然后主行为树只写：

```
Root└── Fallback    ├── StartPreviewStream    └── ReportPreviewFailed
```

这样更清晰。

生活例子：

“做饭”这个大任务可以拆成子任务：

```
买菜备菜炒菜洗碗
```

其中“炒菜”又可以封装成：

```
热锅倒油放菜翻炒调味出锅
```

通俗理解：

> **SubTree 就是把一坨复杂逻辑打包成一个模块。**

# 八、行为树和状态机的区别

## 16. 状态机：适合简单流程

状态机像这样：

```
空闲状态↓启动中↓运行中↓异常状态↓停止状态
```

它适合状态少、流程固定的业务。

比如：

```
App 登录状态设备连接状态简单任务状态
```

---

## 17. 行为树：适合复杂任务和异常恢复

行为树更适合：

```
流程多分支多失败恢复多任务可复用动作会持续运行
```

比如机器人导航：

```
尝试规划路径如果失败，清理地图再尝试规划如果还失败，旋转恢复再失败，上报错误
```

用状态机会变得很乱。

用行为树就很自然：

```
Fallback├── 正常导航├── 清图后重试导航├── 旋转恢复后重试导航└── 上报失败
```

通俗理解：

```
状态机更像“流程图”行为树更像“带失败兜底的任务清单”
```

---

# 九、行为树执行逻辑案例

## 18. 用你的推流流程举一个完整例子

假设手机请求预览，行为树可以这样设计：

```
Root└── Fallback    ├── Sequence：正常启动预览    │   ├── HasPreviewRequest    │   ├── IsRK3576Online    │   ├── IsCameraAvailable    │   ├── SendMqttStartStreamCommand    │   ├── WaitStreamStarted    │   └── ReportPreviewReady    │    └── Sequence：失败处理        ├── StopPartialStream        └── ReportPreviewFailed
```

解释一下：

### 正常情况

```
HasPreviewRequest：手机确实请求预览，成功IsRK3576Online：RK3576 在线，成功IsCameraAvailable：摄像头可用，成功SendMqttStartStreamCommand：MQTT 命令发送成功WaitStreamStarted：RK3576 返回启动成功ReportPreviewReady：通知手机可以收流
```

整个流程成功。

---

### 异常情况：RK3576 不在线

```
HasPreviewRequest：成功IsRK3576Online：失败
```

Sequence 失败。

Fallback 会执行第二个分支：

```
StopPartialStreamReportPreviewFailed
```

最后手机收到：

```
预览失败：RK3576 不在线
```

---

### 异常情况：MQTT 命令偶发失败

可以加 Retry：

```
Retry 3 次└── SendMqttStartStreamCommand
```

表示：

```
MQTT 发送失败不要立即放弃，最多重试 3 次。
```

---

### 异常情况：等不到推流启动

可以加 Timeout：

```
Timeout 5s└── WaitStreamStarted
```

表示：

```
5 秒内 RK3576 没有返回推流成功，就判定失败。
```

---

# 十、行为树学习中还需要理解的工程知识

## 19. 同步和异步

很多初学者会犯一个错误：

```
把耗时任务写成阻塞式 Action
```

例如：

```
startStream();while (!streamStarted) {    wait();}return SUCCESS;
```

这样不好，因为整个行为树会被卡住。

更好的方式是：

```
第一次 tick：发起启动命令，返回 RUNNING后续 tick：检查启动状态成功后：返回 SUCCESS超时后：返回 FAILURE
```

你需要理解：

```
同步：我等你做完才继续异步：我先发起任务，后面每次 tick 检查状态
```

机器人系统里，行为树更适合异步模型。

---

## 20. 任务生命周期

每个 Action 通常有生命周期：

```
onStart：第一次进入节点onRunning：任务执行中onHalted：任务被中断
```

比如导航到目标点：

```
onStart：发送导航目标onRunning：检查是否到达onHalted：取消导航任务
```

推流任务：

```
onStart：发送 MQTT 开始推流命令onRunning：等待推流状态onHalted：停止推流或清理资源
```

这个很重要，因为机器人任务经常会被中断。

比如：

```
正在推流客户端突然断开行为树需要 halt 当前推流任务然后执行 StopStream
```

---

## 21. 错误码设计

行为树里最好不要只返回失败，还要记录失败原因。

比如：

```
FAILURE
```

是不够的。

你还需要知道：

```
失败原因是：- RK3576 不在线- 摄像头打不开- MQTT 发送失败- RTP 端口不可用- 客户端断开- 编码器启动失败
```

这些可以写到 Blackboard：

```
error_code = CAMERA_OPEN_FAILEDerror_msg = 摄像头打开失败
```

这样后面的节点可以根据错误码处理：

```
ReportPreviewFailed
```

从 Blackboard 读取错误原因，然后告诉手机。

---

## 22. 日志和可视化

行为树调试时，一定要看：

```
当前 tick 到哪个节点？哪个节点返回 FAILURE？哪个节点一直 RUNNING？哪个条件不满足？
```

否则你会感觉行为树“莫名其妙不执行”。

建议每个节点都打日志：

```
[HasPreviewRequest] SUCCESS[IsRK3576Online] FAILURE[StartCamera] RUNNING[WaitStreamStarted] TIMEOUT
```

用 Groot / Groot2 时，可以看到行为树节点的实时状态，这对初学者非常有帮助。

# 十一、常见节点总结表

|知识点|作用|通俗案例|
|---|---|---|
|Tick|周期性驱动行为树|每隔一会儿看外卖送到哪了|
|SUCCESS|节点成功|水烧开了|
|FAILURE|节点失败|水壶坏了|
|RUNNING|节点执行中|水正在烧|
|Action|执行动作|洗菜、炒菜、启动推流|
|Condition|判断条件|是否下雨、摄像头是否可用|
|Sequence|顺序执行|买票→安检→检票→上车|
|Fallback|失败后换方案|饭店满了就换一家|
|Decorator|给节点加规则|最多重试 3 次|
|Retry|失败重试|网络不好，多发几次|
|Timeout|超时失败|等 5 秒还没响应就放弃|
|Parallel|并行执行|一边开车一边看路|
|Blackboard|共享数据|公共白板记录 IP、端口、错误码|
|Port|节点参数|快递需要收件地址|
|SubTree|封装子流程|把“做饭”拆成“炒菜子流程”|
|Halt|中断节点|客户端断开，停止推流|

# 十二、你可以这样记忆行为树

最简单的记忆方式：

```
Sequence：必须都成功Fallback：谁成功用谁Condition：只判断Action：真干活Decorator：加规则Blackboard：存数据Tick：反复问RUNNING：还没干完
```

再结合你的机器人项目：

```
手机请求预览是 Condition发送 MQTT 命令是 Action检查 RK3576、检查摄像头、发送命令、等待推流用 Sequence正常启动失败后，重启摄像头、重试、上报错误用 FallbackMQTT 发送失败最多重试 3 次用 Retry等待推流启动最多 5 秒用 TimeoutclientIp、rtpPort、streamId、errorCode放 Blackboard
```

# 十三、最适合你练习的 3 个小案例

## 案例 1：机器人启动自检

```
Root└── Sequence    ├── CheckBattery    ├── CheckNetwork    ├── CheckCamera    ├── CheckMotor    └── ReportReady
```

练习重点：

```
ConditionActionSequence
```

# 十四、初学者最容易踩的坑

## 坑 1：把行为树当流程图

行为树不是普通流程图，它是会反复 Tick 的。

错误理解：

```
从上到下执行一遍就结束
```

正确理解：

```
每次 Tick 都会从根节点开始，根据节点状态决定继续、成功、失败或重试
```

---

## 坑 2：Action 写成阻塞函数

错误：

```
StartStream 一直阻塞等待推流成功
```

正确：

```
StartStream 第一次 tick 发起任务后续 tick 检查状态成功返回 SUCCESS没完成返回 RUNNING失败返回 FAILURE
```

---

## 坑 3：没有错误码

只返回 FAILURE 不够。

最好配合 Blackboard：

```
errorCode = MQTT_SEND_FAILEDerrorMsg = MQTT 命令发送失败
```

---

## 坑 4：Sequence 和 Fallback 用反

记住：

```
Sequence：一条路走到底，某一步失败就全失败Fallback：一条路失败了，就换下一条路
```

---

## 坑 5：没有超时

任何等待型节点都应该考虑超时。

比如：

```
WaitCameraReadyWaitStreamStartedWaitMqttAckWaitNavigationResult
```

都应该设置 Timeout。

否则系统可能一直卡在 RUNNING。

---

# 十五、总结一句话

学习行为树，你重点掌握这几个东西就够了：

```
1. Tick 怎么驱动整棵树
2. 节点为什么有 SUCCESS / FAILURE / RUNNING
3. Sequence 表示“全部成功才成功”
4. Fallback 表示“失败就换方案”
5. Condition 负责判断
6. Action 负责执行
7. Decorator 负责重试、超时、取反
8. Blackboard 负责节点之间共享数据
9. 异步 Action 负责处理耗时任务
10. SubTree 负责把复杂流程拆小
```

用你的项目来理解，行为树最适合管理这种逻辑：

```
先检查条件再执行动作失败就恢复恢复不了就上报任务执行中持续监控客户端断开后及时清理资源
```

这就是行为树在机器人系统里的核心价值。
